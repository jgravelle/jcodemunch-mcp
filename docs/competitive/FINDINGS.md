# FINDINGS — what the competitive loop needs from the layers it may not edit

The loop never edits the harness runner, its thresholds or corpora, the
standard, the CI gates, the inbound policy, or product source (the brief's
Phase 3 rules). A need in any of those is written here for the human who
owns that layer. `CF-n` numbering; a row is closed by naming the commit
that met it.

| # | Finding | Where | Status |
|---|---|---|---|
| CF-1 | The tier is invoked as `python benchmarks/competitive/run.py`, not `python -m harness compete` as DESIGN D7 wanted: registering a tier means editing `harness/__main__.py` and `harness/tiers.json`, which the build rules leave to the harness owner. Until then the runner writes its own result file and the harness's `latest.json` does not carry a `compete` entry. | `harness/__main__.py` (a `tier_compete` beside `tier_bench`), `harness/tiers.json` (a `compete` list with one step) | OPEN, human |
| CF-2 | `docs/competitive/` was under `docs/*` in `.gitignore`; PR 1 adds the `!docs/competitive/` exception beside the other four. Recorded because a rotation that writes into `docs/` proves nothing by creating the file (CLAUDE.md Practice 5). | `.gitignore` | CLOSED by PR 1 |
| CF-3 | The jcodemunch adapter runs in a fresh subprocess on the runner, not in the D2 container. The container base, its flags and the digest bookkeeping arrive with the first competitor adapter (PR 2a), at which point jcodemunch moves into the same image shape so the sandbox cost is symmetric. Until then the jcm row's `index_cold_seconds` and `latency_call_ms` are not comparable to a containerised competitor's and the summary must say so. | `benchmarks/competitive/adapters/jcodemunch.py`, `sandbox/` | OPEN, PR 2a |
| CF-4 | The proof task set (`tasks/self.json`) scores P1 at FILE level with a 100,000-line tolerance because the self corpus moves every commit and a pinned line would rot. Under the first (many-to-many) F1 the row read grep 0.6538 vs jcm 0.6349; under one-to-one matching (review finding 2) the re-measured result at `cdc6542` reads grep 0.2669 vs jcm 0.3333 (delta -0.0664, band 0.0167, meaningful). Neither number measures retrieval: with ONE expected line per task, precision is 1 over the citation count, so the axis is counting how many lines a tool cites (jcm five symbols, grep every matching line) and the verdict flips with the matching rule. Line-level ground truth with several expected lines per task on pinned corpora (Phase 3 item 3) is the measurement; until then f1_P1 on the self set is reported and must not be read as a lead for either side. | `benchmarks/competitive/tasks/self.json` | OPEN until item 3 |
| CF-5 | `run.py` discovers the shared file set by running jcodemunch's `index_folder` once per corpus, so every row reads the files OUR skip patterns admit (R1's "beyond jcodemunch's standard skip patterns"). A competitor that indexes files we skip is disadvantaged on nothing (its own index sees them) but its `files_indexed` will differ from ours; the summary reports both counts and DESIGN s2's breadth row is where the difference shows. | `benchmarks/competitive/run.py::discover_files` | RECORDED, by design |
| CF-6 | The `tools_list_tokens` axis for jcodemunch is read from `benchmarks/schema_baseline.json` (`full_full`, the shipped default), not measured live over stdio, because the live capture is the bench tier's `schema_baseline_live` step and a second capture would be a second copy of that measurement (R46/R50). A competitor's value WILL be measured live over stdio (DESIGN s2), so the two are the same quantity by different instruments; the first competitor adapter PR adds a live capture for jcodemunch too and this row closes. | `adapters/jcodemunch.py::tools_list_tokens` | OPEN, PR 2a |
| CF-7 | `pytest.mark.timeout` is not registered in this repo's pytest configuration (the `--timeout` plugin is absent, CLAUDE.md "Tests"), so the end-to-end test bounds its own subprocess with `timeout=580` instead. If the full tier ever gains a per-test timeout, this test wants one. | `tests/test_competitive_tier.py` | RECORDED |
| CF-8 | The stability rule (spread within 10% of the row's own median) marks every sub-millisecond latency row unstable: grep's per-call median is 0.34 ms with a 0.11 ms spread, read-all's 35.96 ms with 5.37 ms, both on the re-measured result at `cdc6542`. The rule is doing what DESIGN s5.1 says, so a fast tool's latency can never be called a meaningful gap on a noisy box; whether an absolute floor on the spread (in ms) belongs beside the relative one is a Phase 4 question, answered from three CI runs, never from one box. | `benchmarks/competitive/score.py::_stable` | OPEN, Phase 4 |
